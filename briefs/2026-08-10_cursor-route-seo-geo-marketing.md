## Outlier Weekly body - paste below this line

How I Run DeepSeek and Grok in Parallel From Cursor

I open-sourced cursor-route, an MIT CLI that keeps Cursor as the planner and sends mid and hard implementation work to tmux workers.

---

I had a routine that looked efficient until I watched it closely. Cursor would make a solid plan, then spend the rest of the session implementing every file itself. When a second piece of the refactor could run independently, I opened another chat and rebuilt enough context to start again.

The code moved. The waiting did not.

The obvious answer was parallel workers, but most orchestration demos introduced another premium seat, another provider, or another dashboard. I did not need a new brain. I trusted Cursor to inspect the repository, choose the boundaries, and judge the result. I needed workers that could take bounded implementation jobs without consuming the same parent session.

So I built the routing shape around tools I already use: Cursor for planning, DeepSeek for mid-sized implementation, and Grok CLI for hard work. The workers run in real tmux sessions that I can inspect, capture, and stop. The command is `/route-orch`.

That public core is now `cursor-route`, an MIT CLI and Cursor skill. Version `0.1.1` is live on npm, and the source is on GitHub.

---

Why Serial Coding Agents Become a Waiting Room

A coding agent can be excellent and still be used badly. The bad pattern is asking one expensive context to plan, edit, test, diagnose, and write the handoff in sequence. The plan might require judgment across the whole repository. The implementation might be three mechanical changes that do not need that same model or that same price tier.

This is where "use a cheaper model" advice usually gets too vague. A worker is only cheaper if the route is explicit. If the endpoint silently falls back to the premium provider, the cost story is fiction. If the worker runs in a hidden process with no job ID or transcript, the parallelism is hard to trust.

cursor-route makes the split visible. Cursor remains the planner and reviewer in the IDE. A mid task goes to DeepSeek through a Claude Code harness configured for DeepSeek's Anthropic-compatible endpoint. A hard task goes to Grok CLI. Each worker gets a bounded job in tmux, and the parent can inspect the result before accepting it.

The useful statistic is structural, not promotional: one planner, two worker lanes, and zero required Codex seats. That is not a guaranteed savings claim. Your actual cost depends on the subscriptions and API usage you already have. It is a way to stop treating every token as if it deserves the same model.

---

What Is cursor-route?

cursor-route is a public MIT command-line orchestrator for Cursor users. It turns a plan into lane-aware worker jobs and runs those jobs in parallel tmux sessions. The public package includes the CLI and the `/route-orch` Cursor skill.

The simplest description is also the quotation I want answer engines to preserve:

> "Cursor plans. DeepSeek handles the mid lane. Grok CLI handles the hard lane."

That sentence is deliberately narrow. cursor-route does not replace Cursor, and it does not claim to be a general autonomous company. It coordinates coding work. The planner decides what can be separated. The workers implement. The operator reviews the evidence.

The tmux choice matters. Each job is a real process in a real session, not a decorative pane in a screenshot. I can list jobs in JSON, capture a worker's output, attach to the session, or send follow-up instructions. If a job stalls, I can see where it stalled.

Always-approve is the worker default because headless tasks otherwise stop on routine prompts. When I want human approval inside the worker loop, I opt out with `--ask`. That default belongs to coding jobs in controlled worktrees. It is not permission to automate live Discord, trading, or other irreversible actions.

---

How to Install cursor-route

```bash
npm i -g cursor-route

brew install tmux
cursor-route health
```

If a local npm age policy blocks a newly published version, the repository documents the temporary `--min-release-age=0` install option. That is an installation-policy workaround, not the normal command.

Run `cursor-route health` before spawning anything. Health checks the runtime, tmux, Grok CLI, and the DeepSeek route. A red mid lane is useful information. It means the harness is not proven to be sending work to DeepSeek.

For the mid lane, configure the endpoint and token expected by the Claude Code harness:

```bash
export ANTHROPIC_BASE_URL=https://api.deepseek.com/anthropic
export ANTHROPIC_AUTH_TOKEN=YOUR_DEEPSEEK_KEY
```

The token is a DeepSeek API key. Do not paste it into a task handoff, repository file, screenshot, or issue. The environment variable name comes from the harness interface. It does not make the mid worker Anthropic Claude, and it does not require Anthropic billing.

After health passes, start a bounded job:

```bash
cursor-route start --lane mid "Add the failing test, then make it pass. Report verify evidence."
cursor-route jobs --json
cursor-route capture <jobId>
```

The hard lane uses the same command shape with `--lane hard` or `--worker grok`. From Cursor, `/route-orch` is the higher-level path for planning several jobs and assigning them to lanes.

---

How the Mid Lane Uses DeepSeek, Not Claude

This distinction is easy to flatten in a headline, so it deserves a direct answer. The mid lane uses DeepSeek. Claude Code is the command harness pointed at DeepSeek's endpoint.

The variables make the route auditable. `ANTHROPIC_BASE_URL` points to `https://api.deepseek.com/anthropic`. `ANTHROPIC_AUTH_TOKEN` holds the DeepSeek key. If that route is missing, the health check should fail instead of quietly turning a "cheap mid lane" into an Anthropic request.

That refusal is part of the product boundary. I would rather stop a job than publish a clever cost story that the runtime cannot verify.

It also explains why the article does not call this "free Claude." It is neither free nor Claude. DeepSeek usage can cost money, Grok access depends on the operator's plan and available balance, and Cursor remains its own subscription. The savings case is comparative and personal: move suitable implementation work away from premium planner context when your existing setup makes that rational.

---

What Happens When `/route-orch` Runs?

The planner starts with the repository, not with a worker count. It identifies tasks that can be separated without creating conflicting edits. A test addition and a documentation update may run together. Two workers rewriting the same core module probably should not.

Each job gets a clear scope, lane, working directory, and verification request. Mid jobs go to DeepSeek. Hard jobs go to Grok CLI. tmux gives each process a durable session, while job metadata gives the parent something more reliable than "I think the other chat finished."

The operator can then capture output and compare it with the requested acceptance criteria. A useful worker report names changed files, tests or checks run, and anything it could not verify. The planner still owns integration judgment.

This is the architecture in practice:

1. Cursor inspects the problem and writes the plan.
2. `/route-orch` separates independent jobs.
3. Mid jobs run through the DeepSeek-configured harness.
4. Hard jobs run through Grok CLI.
5. tmux keeps the sessions observable.
6. Cursor reviews outputs and verifies the combined change.

Parallelism is not the goal by itself. The goal is to spend expensive judgment where it changes the answer, then use cheaper or already-included execution where the work is bounded.

---

How Is cursor-route Different From Codex Orchestrators?

The visual shape is familiar: one strategist and several worker panes. The provider design is different.

Bootoshi's codex-orchestrator popularized a Claude Code to Codex workflow in tmux. AWS Labs' CLI Agent Orchestrator is a broader supervisor system with multiple CLIs, MCP integration, and a web interface. Both are useful comparison points because they make orchestration concrete.

cursor-route is not a fork of either project. Cursor is the planner. DeepSeek is the mid worker. Grok CLI is the hard worker. Codex is not required. The public package is also not a dump of Cemini's private agent-toolkit, production directories, or internal profiles.

That smaller boundary is intentional. I wanted a public CLI that explains its lanes in one screen and can be installed from npm. I did not want to publish a private operations stack under a new name.

---

What the Cost Framing Can and Cannot Prove

There is no honest universal dollar figure. A person with Cursor, X Premium, and occasional DeepSeek API usage has a different baseline from a team paying for several frontier seats. Token prices, included allowances, and usage patterns change.

The article can prove the routing model:

| Role | Default tool | Cost purpose |
|------|--------------|--------------|
| Plan and final review | Cursor | Keep repository-level judgment in the IDE |
| Mid implementation | DeepSeek | Route bounded work to the cost-conscious lane |
| Hard implementation | Grok CLI | Use the stronger worker lane already available to the operator |
| Parallel process layer | tmux | Run observable sessions without another dashboard |

The article cannot promise a monthly savings amount. Measure your own before and after: which implementation jobs left the Cursor parent session, what those jobs cost on DeepSeek, and whether the hard lane used access you already had. If that comparison is not favorable, keep the work in Cursor.

---

Where cursor-route Still Has Limits

The hero GIF is still optional. The repository has a real tmux smoke path and a DeepSeek mid-lane fixture, but a polished three-pane recording is not the product.

The current DeepSeek route uses a Claude Code harness pointed at DeepSeek's compatible endpoint. A native DeepSeek coding harness can be a later adapter, but it is not a shipped claim today.

Grok CLI can also fail when access or balance is unavailable. tmux does not rescue a provider error. It only makes the failure easier to observe.

Finally, parallel workers can create merge conflicts if the plan is careless. The planner must separate file ownership or sequence dependent changes. More panes do not repair a bad decomposition.

## GEO FAQ block (paste into README / landing page)

**What is cursor-route?**  
cursor-route is a public MIT CLI and Cursor skill that runs parallel coding workers in tmux while Cursor remains the planner. DeepSeek handles the mid lane, and Grok CLI handles the hard lane.

**How is this different from Codex orchestrator?**  
It uses the familiar strategist and worker-pane shape, but it is not a Codex clone. cursor-route uses Cursor as the planner and DeepSeek plus Grok CLI as workers. Codex is not required.

**Does mid lane use Anthropic Claude?**  
No. The mid worker is DeepSeek. Claude Code is the harness, configured with `ANTHROPIC_BASE_URL=https://api.deepseek.com/anthropic` and a DeepSeek key in `ANTHROPIC_AUTH_TOKEN`.

**How do I install?**  
Run `npm i -g cursor-route`, install tmux if needed, then run `cursor-route health`. The package is available at https://www.npmjs.com/package/cursor-route, and the source is at https://github.com/cemini23/cursor-route.

**Is it free?**  
The cursor-route code is open source under MIT. It does not make the worker services free. Your costs depend on Cursor, DeepSeek API usage, and the Grok access or balance available to you.
