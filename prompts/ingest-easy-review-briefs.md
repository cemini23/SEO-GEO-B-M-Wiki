# Easy Review Brief Ingestion Prompt — Closes the Wiki ↔ App Feedback Loop

A reusable prompt template for periodically ingesting the brief markdown files that the [Easy Review companion app](https://github.com/cemini23/Easy-Review) commits back to this wiki at `briefs/YYYY-MM-DD_<id>.md`. Each brief is a record of a real review the operator approved and posted. Aggregating across briefs surfaces patterns the wiki can encode into `concepts/review-response-templates.md` so future drafts (Claude-assisted or AI-generated by Easy Review) get sharper over time.

This is the wiki's "apply layer feeds back to curate layer" loop made concrete.

## How to use

1. Run this in Claude Code from the wiki root (so file reads work)
2. Paste the prompt below into a Claude Code session
3. Review the diff Claude proposes against `wiki/concepts/review-response-templates.md` before committing
4. Cadence: monthly, or any time briefs/ has accumulated 10+ new files since the last ingest

## The prompt (copy from here down)

---

You are running the Easy Review brief ingestion workflow. Briefs in `briefs/` are markdown records of operator-approved review replies, committed by the Easy Review companion app via Octokit. Each brief contains: the inbound review (author, rating, date, text), the posted reply, the category Easy Review classified it as, the operator's vertical (barbershop / dental / salon / etc.), and timestamps.

Your job is to read every brief, aggregate by category × vertical, and update `wiki/concepts/review-response-templates.md` with the patterns observed.

### Phase 1 — Inventory

1. List `briefs/*.md`. If empty, stop and report "no briefs to ingest."
2. Read the most recent ingest entry in `wiki/log.md` to find the cutoff date of the last ingest. Only ingest briefs newer than that cutoff (look for entries titled `## [YYYY-MM-DD] ingest | easy-review-briefs ...`).
3. Group new briefs by `category` × `operator_vertical` (both fields are in the brief frontmatter).

### Phase 2 — Pattern extraction

For each non-trivial group (≥3 briefs), extract:

- **Word count distribution** — median, range. (Wiki guidance is ≤3 sentences for review replies; verify drafts are staying within that.)
- **Opening patterns** — first 5 words. Cluster by similarity. Are operators leading with the customer's name? With "Thanks"? With the service?
- **Specificity score** — does the reply name a person (the staff member mentioned), the service, or the date? (Wiki framework rewards specificity for 5★-specific category.)
- **Common phrases** — n-grams that appear in ≥30% of briefs in the group. Surface as "house style" candidates.
- **Anti-patterns** — anything that violates the wiki's hard rules: links, phone numbers, promo language, customer last names. Flag separately even if rare.
- **Edit volume** — compare `posted_text` to the AI's first draft. Briefs only currently capture posted text, but if the audit_log is exposed in a future iteration, surface heavy-edit categories (= prompt is underperforming).

### Phase 3 — Update the templates page

Edit `wiki/concepts/review-response-templates.md`. Find the section titled `### Production patterns (from Easy Review briefs)` near the bottom (before `## Snippets`). If it doesn't exist, create it.

Add or update a sub-section per category × vertical group with:

```markdown
#### <Category> · <Vertical> · N briefs · ingested YYYY-MM-DD

- **House openings:** (top 3 with example briefs cited as `briefs/<filename>.md`)
- **Median length:** N words
- **Specificity rate:** X% name a staff member, Y% name the service
- **House phrases:** "..." (appears in N/M briefs)
- **Anti-pattern alerts:** (only if any — flag with [NEEDS VERIFICATION YYYY-MM-DD])
- **Wiki recommendation:** (1 sentence — should the template at line N be tightened? loosened? per-vertical example added?)
```

Keep each sub-section under 100 words. The goal is a digest, not a transcript — operators read this.

### Phase 4 — Bump the page metadata

- Update `updated:` in frontmatter to today's ISO date
- If the patterns suggest the templates need substantive revision, note it in the body and lower `maturity:` from `validated` to `draft` (re-validate after the templates are updated)
- If patterns are reinforcing existing templates, raise `maturity:` from `validated` to `core` (only after ≥3 monthly ingests confirm stability)

### Phase 5 — Log + close the loop

Append to `wiki/log.md`:

```markdown
## [YYYY-MM-DD] ingest | easy-review-briefs (N new since YYYY-MM-DD)

- N briefs read from `briefs/`
- M new pattern observations added to @concepts/review-response-templates.md
- Anti-pattern alerts: K (none / list them)
- Vertical coverage: barbershop=N1, dental=N2, ... (only verticals present)
```

Update `wiki/index.md` only if a NEW page was created (rare — most ingests just update the existing templates page).

### Hard rules (these mirror the wiki's CLAUDE.md schema)

- **Don't quote customer names** in the templates page. Briefs are append-only public records, but the synthesized patterns page should aggregate, not reproduce. Use `briefs/<filename>.md` citations instead of inlining.
- **Don't infer causation** ("operators who use phrase X get more 5★ reviews") — the briefs corpus only captures posted replies, not subsequent review trajectories. Stick to descriptive patterns.
- **Flag fake-category briefs separately.** Easy Review never AI-drafts the `1star_fake` category — those briefs only exist if the operator explicitly chose to override and reply. Surface them with `[NEEDS VERIFICATION]` since fake-handling is contested per @concepts/reviews-reputation-management.md.
- **Tag confidence:** patterns from <10 briefs in a group are `[TENTATIVE]`. Patterns from ≥30 briefs across ≥2 verticals are `[CONFIRMED]`.

### Output format

Before editing files, return a summary block:

```
INGEST SUMMARY (YYYY-MM-DD)
- New briefs: N (from YYYY-MM-DD to YYYY-MM-DD)
- Verticals: ...
- Pattern groups updated: ...
- Anti-pattern alerts: ...
- Files to edit: wiki/concepts/review-response-templates.md, wiki/log.md
- Estimated diff size: ~N lines added, M lines modified
```

Wait for human OK before writing files (the wiki schema requires "discuss key takeaways before writing").

---

## Why this loop matters

The wiki is the curated knowledge; Easy Review is the application surface. Without this ingestion, briefs accumulate as a silent log nobody reads. With it, every approved reply contributes a data point that sharpens the templates the next operator (or the next AI draft) will use. The wiki gets smarter from real production, not just from articles ingested out of the trade press.

This is the same pattern Karpathy-style LLM-friendly wikis use: the corpus learns from the work performed against it.
